# 跟随发送与运行中插话设计

> 状态：设计定稿（2026-10-28），一期已实现、未提交，Electron 实机未验；2026-10-29 交互改版（第 3 节、第 15 节）。本文是实现依据；后续改动如需偏离，先改本文再改代码。实现与本文的差异见第 14 节。

## 1 背景与目标

现在智能体运行时，输入框整体禁用，只剩一个停止按钮。用户想到补充要求（“主角名字改成林舟”“第三段别动”）只能等它跑完，或者停掉重来。

目标：创作空间（短篇、剧本、长篇）、素材库、技能库的对话里，运行期间也能继续打字、发送：

- **插话（默认）**：运行中发送的消息直接显示在对话里，注入本轮循环，在智能体下一次调用模型前进入上下文，不用等本轮结束。
- **跟随发送（兜底）**：不能或没赶上插入本轮的消息，本轮结束后自动作为下一条消息发出。

一期不做的内容见第 11 节。

## 2 现状

### 2.1 界面

- 三处入口共用 `AgentConversation.vue` → `ConversationComposer.vue`：短篇、剧本、素材库、技能库经 `WritingWorkspaceModule`，长篇经 `LongWorkspaceModule`。只改一个输入框即可覆盖全部入口。
- 运行中（`responding`）textarea、附件、语音、正文引用的移除按钮都被 `disabled`；发送按钮由 `v-if="!responding"` 换成停止按钮。
- `useAgentConversation` 的 `canSend` 要求 `!isBusy && !hasPendingEditReview`，`sendMessage` 直接读取 `ctx.draft` 作为消息内容，成功后清空草稿。
- 发送前由 `useShortConversationCoordinator` / `useLongConversationCoordinator` 组装作品上下文（文档快照、可读技能与素材、资料库上下文、审批模式），再进入 `sendMessage` → `submitConversationTurn` → `session.prompt`。

### 2.2 运行时

- Pi `Agent` 自带两个队列：`steer()` 在当前助手回合的工具全部执行完后、下一次模型调用前注入；`followUp()` 在智能体本要停下时再接一轮。项目里 `required-output-guard`、`subagent-reply-guard` 已经在用 `steer()`。
- Pi 的 steering 队列默认 `one-at-a-time`，每个注入点只取一条。
- Pi 的 `prompt()` 开头会先取一次 steering 队列：上一轮遗留的插话会被带进下一轮。
- 失败重试 `removeFailedAssistantFromTranscript` 只删除失败的那条助手回复，之前已注入的用户消息保留。
- 运行控制命令已有先例：`session.user_input_response` 由 Main 转成 `agent.user_input_response`，交给 Agent Utility 按 `sessionId` / `runId` 权威校验后处理。
- 压缩切点 `findCutPoint` 把任何 `role: "user"` 的消息都当作边界。

## 3 交互定义

> 2026-10-29 按用户反馈改版：取消输入框上方的排队区和“下一轮 / 插入中…”等状态标签，运行中发送的消息直接作为用户气泡出现在对话里，并默认插入本轮。下文为改版后的定义。

### 3.1 输入框与主按钮

运行中，输入框、`/` `@` `#` 引用菜单、正文引用、附件和语音转写都可用（它们只往草稿里写）。模型、思考档位、温度、联网和团队模式仍然锁定，因为它们属于正在跑的这一轮；消息作为新一轮发出时，按当时的选择生效。

| 状态 | 输入框内容 | 主按钮 | Enter |
| --- | --- | --- | --- |
| 空闲 | 任意 | 发送（现状） | 发送 |
| 运行中 | 空（无文字、附件、正文引用） | 停止 | 无动作 |
| 运行中 | 有可发送内容 | 发送 | 发送 |

按钮只由“输入框是否有可发送内容”决定，尺寸不变，切换时不出现中间态。

### 3.2 发送后的显示

- 运行中点发送，输入框清空，消息立刻以用户气泡出现在对话末尾（右侧），样式与普通用户消息一致，不带任何状态文字。正在执行的回复留在气泡上方继续运行。
- 智能体在当前步骤结束、下一次调用模型前读到这条消息（3.3）。送达后，气泡成为本轮时间线里的一步，位置不动；之后的输出接在气泡下面。
- 本轮结束后，处理过程照常折叠为“已处理 X 秒”，但气泡留在折叠区外：处理过程在气泡处分成前后两段，各自计时，最终回答接在最后。
- 气泡出现时，消息列表回到底部并继续跟随，与普通发送一致。失败、提示一律走 toast。
- 未送达的消息最多 5 条，超出时 toast 提示，内容留在输入框。

### 3.3 送达方式

- **默认插入本轮**：发送即提交 `session.steer`。它不打断正在输出的模型或正在执行的工具；正在跑子智能体或等待用户回答提问时，要等这个工具返回后才注入。
- **作为下一轮**：含图片附件的消息不能插入本轮；本轮先结束、没赶上注入的消息也一样。它们在本轮正常完成后自动作为下一条消息发出（3.4），气泡位置不变，回复接在它下面。不弹提示。
- 本轮还没受理（只有 attempt，还没有 `runId`）时就发送，控制器先记下请求，拿到 `runId` 后再提交。
- 插入请求被拒（非“本轮已结束”类错误）时，用 toast 提示一次，消息改为下一轮发送。

### 3.4 作为下一轮发出

本轮正常完成（`agent.completed`）后，同时满足以下条件时，自动发出第一条等待中的消息：

- 队列没有暂停；
- `canSend` 成立：没有待审提案，没有延迟保存，不忙；
- 这个会话仍是当前的发送目标（与 coordinator 的 `sendTargetIsCurrent` 判断一致）。

发出走 coordinator 的正常发送路径，作品上下文、附件、审批模式、团队模式和模型都在那一刻读取，与用户手动发送完全一致。每轮只发一条，剩下的等下一轮完成再发。新一轮受理时，气泡换成正式的用户消息，同一帧完成。

### 3.5 停止、失败与待审

- **用户停止**或**运行失败**（非用户停止的 `agent.error`）：队列暂停，未送达的消息按顺序放回输入框开头，与正在输入的内容用换行分隔，附件一并放回（超过单条上限时只放回能容纳的部分，并用 toast 说明）。气泡随之消失，用户可以修改后再发。
- **作为下一轮发出失败**：同样放回输入框。
- **本轮结束但有待审提案**：气泡保留，等用户处理完全部提案、`canSend` 恢复后自动发出。
- **空闲时在输入框发送**：直接发送，与现状相同。

### 3.6 对话流里的插话

已注入的插话作为本轮助手消息时间线（`processingSteps`）里的一步，显示为普通用户气泡，不加“你补充了”之类的标签。它不算一个新回合，回合导航不变，也不支持编辑或重发。

## 4 送达语义：恰好一次

**不变量**：一条插话要么在本轮被注入（Renderer 在本轮终止事件之前收到它的 `agent.steering_delivered`），要么完全没进入上下文、由 Renderer 改作下一条消息。不会两边都发生，也不会丢。

实现依赖四点：

1. **受理闸门**：Agent 只在本轮未终止时受理插话；收尾阶段（`runAgentWithTurnRetries` 返回后）关闸，之后到达的拒绝为 `agent.steering_closed`。受理后放入 Pi steering 队列，`steeringMode` 设为 `"all"`，同一注入点一次带上全部已受理的插话。
2. **注入判定**：Kernel 用 WeakMap 记住自己入队的 `UserMessage` 对象，Pi 对该对象发出 `message_end` 时，发 `agent.steering_delivered`。它和终止事件走同一个有序事件队列，必然先于 `agent.completed` / `agent.error` 到达。`required-output-guard` 自己的 steer 不在 WeakMap 里，不受影响。
3. **收尾清队**：Kernel 在 cleanup 和每次 `startRun` 前调用 `agent.clearSteeringQueue()`。否则残留插话会在下一次 `prompt()` 开头被注入，同时 Renderer 又补发一次，造成重复。
4. **Renderer 以终止事件为准**：终止时仍处于 `steering` 的条目一律退回队列最前；之后才到达的受理回复按 `(runId, steerId)` 丢弃。

| 时机 | Agent | Renderer 结果 |
| --- | --- | --- |
| 运行中受理，下一次模型调用前被取出 | 发 delivered | 移出队列，显示在本轮 |
| 受理时本轮最后一次取队列已过，随即结束 | 收尾清队，不发 delivered | 终止时退回，作为下一条消息 |
| 命令到达时本轮已终止或在收尾 | 拒绝 `run_not_active` / `steering_closed` | 退回队列 |
| 受理回复晚于终止事件到达 | — | 丢弃回复，条目已按终止处理 |
| 模型调用失败后重试 | 已注入的插话留在上下文；等待重试期间受理的，在 `continue()` 开头注入 | 正常 |
| 上下文压缩 | 插话作为普通用户消息参与压缩，但不作为切点（见 6.3） | 正常 |

## 5 协议（contracts）

新增 `packages/contracts/src/session/steering.ts`：

- `SessionSteerCommandPayloadSchema`：`sessionId`、`runId`、`steerId`（≤120）、`message`（1 到 `SESSION_PROMPT_MAX_MESSAGE_LENGTH`），以及可选 `attachments`（仅文字类，条数与总字数上限与普通消息相同）。
- `SessionSteerAcceptedPayloadSchema`：`sessionId`、`runId`、`steerId`、`acceptedAt`。
- 命令信封 `session.steer`（Renderer → Main）和 `agent.steer`（Main → Agent），`context.sessionId` / `runId` 必须与载荷一致，校验方式与 `session.abort` 相同。
- 事件 `agent.steering_delivered`：`messageId`、`steerId`、`content`、`attachments`（仅元数据）、`deliveredAt`、`runtime`。事件带上文字，Renderer 不依赖内存中的队列条目也能写入时间线。
- 错误码：`agent.run_not_active`、`agent.steering_closed`、`agent.steering_limit`（每轮最多 20 条）、`agent.steering_unsupported`（扩展域运行），预算超限沿用 `session.prompt_budget_exceeded`。
- 将上述命令和事件加入 commands / envelopes 联合类型，Renderer 需要的运行时值从 `renderer.ts` 导出；Preload 新增 `session.steer(payload)`，请求和响应都要校验。
- 不向 `session.prompt` 载荷或 `WorkspaceRuntimeContext` 添加任何字段。

## 6 Main 与 Agent

### 6.1 Main

`ipc/session-commands.ts` 新增 `session.steer` 分支，照搬 `session.user_input_response`：用 `conversationPromptBudgetError` 复核消息与文字附件，转成 `agent.steer` 交给 Agent Utility，超时 10 秒，回执的 `sessionId` / `runId` / `steerId` 必须与请求一致。

### 6.2 Agent Utility

- `agent-entry.ts` 已有 199 行，接近入口上限，所以把 `agent.abort`、`agent.user_input_response`、`agent.steer` 三个运行控制分支拆到 `utilities/agent-run-control.ts`。
- `agent.steer` 要求 `runs.activeRun(sessionId) === runId`，扩展域运行一律拒绝；通过后调用 `runtime.steer(payload)`。

### 6.3 运行时

- `AgentRuntime` 接口新增 `steer(payload)`；`PiAgentRuntimeAdapter` 持有 `runId → 插话句柄` 的注册表，与 `userInputBroker` 并列。
- 新增 `kernel/run-steering.ts`，提供 `createRunSteering({ agent, target, emit, messageId, runtime })`，返回：
  - `submit(payload)`：检查闸门与上限，构造用户消息，`agent.steer()`，并记入 WeakMap；
  - `observe(event)`：遇到已登记消息的 `message_end` 时发 delivered；
  - `close()`：关闸并清队。
- `run-kernel.ts`（已有 512 行）只加接线：注册与注销句柄，`onEvent` 里调用 `observe`，收尾和 cleanup 时 `close`，准备 agent 时设 `steeringMode = "all"` 并清队。
- 插话内容由 `prompts-user-message.ts` 新增的 `buildSteeringUserMessageContent` 生成，文字附件的渲染与普通消息共用 `buildRawUserText` 的格式：

  ```
  【运行中用户补充】
  用户在你工作过程中追加了下面的要求。已经执行的工具调用不会撤销；请据此调整接下来的步骤，与先前要求冲突时以这条为准。

  {用户文字}
  {文字附件}
  ```

- **压缩**：`ConversationContextState` 记录插话消息（WeakSet）。`findCutPoint` 的边界判断排除这些消息，让它们和本轮中间内容一样处理；否则切点可能落在一轮中间，却被当作整轮边界，导致检查点与 Renderer 的 `keepFrom` 对不上。
- 插话不转发给正在运行的子智能体，由主智能体在之后的派工里转述。

控制器新增：`queuedMessages`、`canQueue`、`queueDraft(attachments)`、`withdrawQueued(id)`、`steerQueued(id)`、`setFollowUpDispatcher(dispatch)`。

- 运行生命周期的钩子：受理（拿到 `runId`，补交挂起的插话请求）；终止（completed / stopped / error，退回未注入的条目，决定是否暂停）；`canSend` 变化（用于待审结束后发出）。

### 7.2 发出排队消息

- 两个 coordinator 各自注册 dispatcher：短篇、剧本、素材库、技能库在 `useShortConversationCoordinator`，长篇在 `useLongConversationCoordinator`。dispatcher 走与输入框发送相同的上下文组装路径，返回“已受理”“失败”或“延后”。目标不是当前会话时返回延后，条目保留，等会话重新成为当前目标再发。
- `sendMessage` 增加显式内容参数：排队消息的内容来自条目，不读也不清空 `ctx.draft`（用户可能正在输入下一条）；失败时不回写草稿，交给队列处理（放回最前、暂停、toast）。

## 8 记录、恢复与同步

- **持久化**：`parse-message.ts` 解析 `user_note` 步骤。旧版本只保留已知步骤类型，打开新记录时只是不显示插话，不会报错。
- **冷启动恢复**：`history.ts` 的 `buildConversationRestore` 把助手消息里的插话并入它前面那条用户消息，追加为“【运行中补充】”段落。恢复历史只带最终文本，把补充放在回复之前，顺序是真实的；合并成一条可以避免连续两条用户消息（部分 provider 要求角色交替）。合并后的长度计入历史上限。
- **重发与改写**：改写某条用户消息会截掉它之后的整轮，插话随之消失，符合预期。失败轮次重发时，用同一个拼接函数把该轮已注入的插话并入重发内容。
- **导出**：`conversation-export` 把插话渲染成引用块“> 运行中补充：…”。
- **双端同步**：`desktop-records.ts` 的 `valid()` 会丢弃同步 schema 不认识的步骤，一期无需改协议，也不影响旧版桌面和手机端；对端只是看不到插话。二期在共用模块加入 `user_note`，桌面和手机同发。实现时需确认本机记录不会被自身的同步投影回写覆盖。
- **排队条目不落盘**：控制器销毁（关闭作品、关闭应用、清理会话）前，把未发出条目的文字按顺序并回草稿，必须在停止持久化之前完成，保证不丢字。附件不保留，现有草稿附件同样不落盘。

## 9 边界情况

- **子智能体或提问卡片阻塞**：插话要等 `spawn_subagent` 或 `ask_user` 返回才注入，气泡可能在对话末尾停留较久。
- **切换会话或作品**：插话照常注入；跟随发送等会话重新成为当前目标时再发。
- **审批、写锁、跨阶段确认**：都不变。插话不带提案结算，结算仍由下一条正常消息携带（`collectProposalSettlements`）。
- **用量与预算**：插话计入本轮上下文和用量；Renderer 入队时按 `conversationPromptError` 预检，Main 复核。
- **用户停止时有消息正作为新一轮发出**：它已经是新一轮的用户消息，停止的是这一新轮。
- **上限**：未送达的消息 5 条，每轮插话 20 条，超出时 toast 提示。

## 10 验证

- **contracts**：载荷上限、信封与载荷一致性、新事件解析。
- **pi-runtime-adapter**（Faux 模型）：
  - 工具执行中提交，下一次模型调用的上下文包含插话，且 delivered 先于 completed；
  - 最后一次取队列之后提交，不发 delivered，收尾清队，下一次 `prompt()` 不带残留；
  - 失败重试后插话仍在上下文中；
  - `steeringMode: "all"` 一次注入多条；
  - 扩展域与已终止的运行被拒；
  - 压缩不以插话作为切点。
- **Renderer 单测**：
  - 入队与删除回填（空输入框与非空输入框）；
  - 跟随发送每轮一条；
  - 停止和失败后暂停，有待审提案时等待；
  - 终止时 `steering` 条目退回，过期回执被丢弃；
  - 非当前目标时延后；

## 14 实现记录（2026-10-28）

与前文的差异和补充：

- **重发**：现有界面只有“编辑用户消息后重发”，它按第 8 节规则截掉整轮，插话随之消失；没有单独的失败重试入口，所以“重发并入插话”无处可挂，未实现。
- **导出**：对话导出是控制器数据的 JSON 快照，`user_note` 步骤随消息原样导出，无需单独渲染。
- **运行时接口**：`steer` 加在 `PiAgentRuntimeAdapter` 上（与 `resolveUserInput` 并列），`AgentRuntime` 接口只有 `describe` / `start`，未改。
- **Main**：`session.abort`、`session.user_input_response`、`session.steer` 一起移到 `ipc/session-run-control-commands.ts`，共用一套“转给 Agent、核对回执”的流程。
- **输入框**：会话控制器的 `followUps` 经 `AgentConversation` 传给输入框，不经过 `WorkspaceShell`（行数预算 2800）。没有传入 `followUps` 的输入框保持旧行为：运行中整体禁用、变灰。
- **排队发出**：控制器上的 `queuedDispatch` 让 `sendMessage` 改读条目内容、不清空草稿；两个 coordinator 的“输入已变化”检查在 `followUps.dispatching` 为真时跳过草稿比对。排队消息因上下文不就绪等原因未能发出时，队列暂停，等用户手动发送。
- **未落盘**：关闭作品时，排队文字经 `dispose` 并回草稿；直接退出应用时，Renderer 不销毁控制器，排队中的文字会丢失（运行本身也随之中止）。
- **行数**：`follow-up-queue.ts` 约 340 行，是一个状态机（入队、插话、发出、运行收尾），未拆；`ConversationComposer.vue`、`run-kernel.ts`、`events.ts` 原本就超出建议上限，本次只增加接线。

## 15 交互改版（2026-10-29）

用户反馈：排队区和“插入中…”“下一轮”等状态多余，插话气泡上的“你补充了”也不需要。改为发送即显示为用户气泡、默认插入本轮（第 3 节已按此重写）。实现要点：

- **状态机**：`follow-up-queue.ts` 的 `enqueue` 在运行中直接转入 `steering`（含图片的保持 `queued`），去掉 `sendNow`、`canSendNow`、`reviewPending`；没赶上本轮时不再弹“没赶上本轮”提示。
- **显示**：删除 `ComposerQueuedMessages.vue`。`ConversationMessageList` 新增 `pendingMessages`，在列表末尾画未送达的气泡；`ConversationSteeringNote` 改为与普通用户消息同样式、无标签。未送达气泡的上边距与送达后在时间线里的位置对齐，送达时同一帧换位，不跳动。
- **结束后保持可见**：`conversationTimelineBlocks` 对已结束的回复按插话拆成“处理段 / 插话 / 处理段”，每段用 `processingSpanLabel` 单独计时；运行中仍是一个实时列表。
- **放回输入框**：`useComposerQueue` 改为监听队列暂停，把未送达的消息连同附件一次放回输入框；没有单条“删除”按钮了。
- **滚动**：`useConversationScrollFollow` 新增 `pendingMessageIds`，出现新气泡时解除锁定并回到底部。
